This page answers the most common questions server administrators and staff run into when running NovaRestore. If you are dealing with an unexpected behavior, a missing snapshot, or a configuration issue, start here.

<AccordionGroup>

  <Accordion title="Why isn't the Discord bot connecting?">
    The Discord bot token must **never** be placed in `config.yml`. Instead, it must be passed as a JVM startup argument to keep it out of version control and accessible log files. Check the following in order:

    1. **Token is in the startup arguments** — Confirm your Paper startup script includes `-Ddiscord.token=YOUR_BOT_TOKEN` in the JVM arguments, before the jar filename.
    2. **Token is valid** — Log in to the [Discord Developer Portal](https://discord.com/developers/applications), open your application, navigate to the **Bot** tab, and regenerate the token if you are unsure.
    3. **Log channel ID is set** — `discord.log-channel-id` in `config.yml` must be the numeric channel ID (right-click the channel in Discord → Copy Channel ID with developer mode enabled).
    4. **Bot has permission in that channel** — The bot needs at minimum **Read Messages**, **Send Messages**, and **Embed Links** in the configured channel, plus **Use Application Commands** if you use slash command interactions.
    5. **Admin role IDs are correct** — `discord.admin-role-ids` must list at least one valid Discord role ID. Requests cannot be approved or denied if no role is authorized.

    After correcting any of the above, run `/invrollback reload` in-game or restart the server. The console will log whether the bot connected successfully.
  </Accordion>

  <Accordion title="A player's death snapshot is missing — why?">
    There are a few reasons a snapshot may not exist:

    - **Retention policy removed it** — Snapshots older than `storage.retention.max-snapshot-age-days` (default: 45 days) are purged automatically. If the player's death was more than that many days ago, the data is gone.
    - **The death happened in a blocked world or game mode** — If `storage.filters.enabled` is `true` and the world or game mode is listed under `blocked-worlds` or `blocked-gamemodes`, no snapshot is saved for deaths in those environments.
    - **The death snapshot was empty** — If `storage.skip-empty-death-snapshots` is `true` (the default), deaths where the player had no items, no XP, and nothing in their ender chest are not recorded. Nothing was lost, so nothing was saved.
    - **The player exceeded the per-player snapshot limit** — `storage.retention.max-snapshots-per-player` (default: 100) caps how many deaths are kept per player. The oldest are removed first when the limit is hit.
    - **The plugin was not loaded at the time of death** — If the plugin was disabled, reloading, or encountered a database error at the moment of death, the event was not captured.
  </Accordion>

  <Accordion title="Why can't a player submit another restore request?">
    NovaRestore enforces a per-player limit on concurrent active requests via the `requests.max-pending-per-player` configuration key (default: 3). If a player already has that many snapshots in `PENDING` state, staff will not be able to submit additional requests for that player until one of the existing requests is resolved (approved, denied, cancelled, or timed out).

    To check the current state of a player's snapshots, use:

    ```bash title="Check player snapshot states"
    /invrollback info <player>
    ```

    Set `max-pending-per-player` to `0` in `config.yml` to remove the limit entirely.
  </Accordion>

  <Accordion title="A request timed out — what happened?">
    If `requests.timeout-minutes` is set to a positive value (default: 1440 minutes / 24 hours), any restore request that remains in `PENDING` state for longer than that duration is automatically expired by the system. When a timeout occurs:

    - The snapshot state is moved back to `OPEN`
    - A `TIMEOUT` entry is written to the audit log with actor `SYSTEM`
    - The player receives an in-game notification (if `notifications.notify-target-player` is `true`)

    The snapshot is fully available again after a timeout — staff can submit a new request for it at any time. Timeouts are designed to prevent the pending queue from filling up permanently when Discord requests go unreviewed.

    If you want requests to never expire, set `timeout-minutes: 0`. Note: if you combine `timeout-minutes: 0` with a positive `max-pending-per-player`, the plugin applies a safety timeout of 1440 minutes automatically to prevent permanent queue blocking.
  </Accordion>

  <Accordion title="A player logged in and received unexpected items">
    This is expected behavior — it means a **queued restore** was delivered. When a Discord admin approves a restore request while the target player is offline, the restore is held in a `QUEUED` state rather than discarded. The next time the player logs in, NovaRestore automatically delivers the approved items and sends them an in-game notification:

    > *"Your approved rollback was restored automatically when you joined."*

    This is not a bug. You can verify what was delivered by checking the audit log:

    ```bash title="Check audit log for delivery"
    /invrollback logs <player>
    ```

    Look for a `DELIVER_*` entry, which will show the restore type and the staff member who approved it.
  </Accordion>

  <Accordion title="Can the same death be restored twice?">
    No — not without explicit staff intervention. Once a snapshot reaches the `RESTORED` state it is **locked**. The inspection menu in-game shows it as already restored and prevents new requests from being submitted for it. This prevents duplicate restores from the same death event.

    If a restore was incomplete (for example, only armor was returned when full contents should have been), a staff member with the `rollback.manage.unlock` permission can unlock the snapshot:

    ```bash title="Unlock a restored snapshot"
    /invrollback unlock <deathId>
    ```

    This returns the snapshot to `OPEN` state and writes an `UNLOCK` entry to the audit log, so there is always a record of who unlocked it and when.
  </Accordion>

  <Accordion title="How do I restore items to an offline player?">
    NovaRestore handles offline players automatically through the queue mechanism. When a Discord admin approves a restore request for a player who is not currently online, the plugin sets the snapshot state to `QUEUED` and stores the approved restore type. The next time that player connects, the items are delivered automatically.

    There is no separate command needed for offline delivery — the approval workflow in Discord handles everything. Staff simply approves the request normally, and the system takes care of the rest when the player logs in.
  </Accordion>

  <Accordion title="The console shows 'unsafe configuration' warnings — what should I do?">
    NovaRestore logs warnings at startup when it detects configuration settings that could lead to operational problems. Common unsafe configuration scenarios include:

    - **`timeout-minutes: 0` with a positive `max-pending-per-player`** — This combination could permanently block new requests if Discord approvals are delayed. The plugin resolves this by applying an effective 1440-minute safety timeout automatically.
    - **`discord.bot-token` set to a literal token value** — The token should only be provided via the JVM argument `-Ddiscord.token=...`, not written into `config.yml`. Having it in the config file is a security risk.
    - **Missing or invalid `log-channel-id`** — The plugin cannot route requests to Discord without a valid channel ID.

    Read the warning message in full — it will specify the exact key and the recommended correction. After fixing the configuration, run `/invrollback reload` or restart the server.
  </Accordion>

  <Accordion title="How do I migrate from the old InvRollback plugin?">
    NovaRestore is a modern rewrite and does not automatically import data from legacy InvRollback installations. The database schema, storage format, and snapshot model are different enough that a direct migration is not straightforward.

    The recommended approach is:

    1. Keep your old InvRollback data directory backed up.
    2. Install NovaRestore fresh — it will create its own database tables (prefixed with `invrestore_` by default).
    3. Operate both in parallel for a transition period if needed, though running two inventory-capture plugins simultaneously is not recommended.
    4. For any critical legacy restores that must be honored, perform them manually using items from your backup before switching over.

    If you are using MySQL, both plugins can point to the same database server as long as the table prefixes are different and there is no schema conflict.
  </Accordion>

  <Accordion title="Does NovaRestore support MySQL?">
    Yes. NovaRestore supports both **SQLite** (the default, file-based) and **MySQL**. To switch to MySQL, update the `database` section in `config.yml`:

    ```yaml title="config.yml — MySQL configuration"
    database:
      type: "MYSQL"

      mysql:
        host: "127.0.0.1"
        port: 3306
        database: "invrestore"
        username: "root"
        password: "your-password"
        parameters: "useSSL=false&characterEncoding=utf8&autoReconnect=true"

        pool:
          maximum-pool-size: 10
          minimum-idle: 2
          connection-timeout-ms: 10000
          maximum-lifetime-ms: 1800000
          keepalive-time-ms: 0
    ```

    MySQL is recommended for networks running multiple Paper servers that share the same database, or for servers that need the performance and tooling of a dedicated database server. SQLite is perfectly suitable for single-server setups.

    After changing the `type`, restart the server. NovaRestore will create its tables in the configured MySQL database automatically on startup.
  </Accordion>
